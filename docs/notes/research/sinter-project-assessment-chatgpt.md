# 1. MCP68 architecture: northbridge/southbridge split

Yes, your model is basically correct.

The platform is:

* **Phenom II**:
    * integrated DDR2/DDR3 memory controller on-die,
    * HyperTransport link outward,
    * no traditional FSB.
* **MCP68**:
    * effectively a unified I/O hub (“single-chip chipset”),
    * combines:
        * PCI/PCIe root functions,
        * SATA/IDE,
        * USB,
        * LPC,
        * ACPI,
        * integrated graphics,
        * SMBus,
        * legacy southbridge glue.

So compared to older Athlon XP/P4 systems:

```
CPU <--FSB--> Northbridge <--PCI--> Southbridge
```

you instead have roughly:

```
Phenom II <--HyperTransport--> MCP68
```

with DRAM directly attached to the CPU.

That part is not myth.

Where people sometimes get confused:

* there _is still_ internal northbridge-like functionality inside the CPU package,
* AMD documentation still talks about “NB frequency”,
* but the motherboard chipset is no longer the memory-controller owner.

So your mental model is sound.

# 2. Writing a bare-metal kernel for MCP68

This is very realistic.

You do _not_ need full chipset docs to get surprisingly far.

The practical bootstrapping sequence is usually:

1. real mode boot stub,
2. switch to protected mode,
3. set up GDT/IDT,
4. basic paging,
5. PCI config-space enumeration,
6. serial console,
7. storage,
8. APIC/SMP later.

The nice thing is that x86 standardized enough of the ugly parts.

## PCI enumeration

You’ll likely use legacy PCI config mechanism #1:

* ports `0xCF8` / `0xCFC`.

That works fine on this era.

Enumerate:

* bus,
* device,
* function,
* vendor/device IDs,
* BARs.

You do not need NVIDIA-specific magic initially.

* * *

## Interrupts

Your instinct is right:

### Early stage

Use:

* legacy PIC (8259-compatible),
* IRQ remapping,
* simple ISR table.

### Later

Move to:

* IOAPIC,
* LAPIC,
* MSI/MSI-X if desired.

You can absolutely bring the system up with only the PIC.

* * *

## Storage

You specifically mentioned IDE mode.

That’s a good choice initially.

AHCI on NVIDIA chipsets is historically annoying compared to Intel.

You’ll save enormous effort by:

* enabling legacy IDE compatibility mode in BIOS,
* speaking ATA PIO first,
* then DMA later.

This is a sane hobby OS path.

* * *

## Things likely to bite you on MCP68

### ACPI weirdness

nForce-era ACPI tables were often ugly.

Don’t assume:

* MADT correctness,
* HPET correctness,
* SCI routing sanity.

Linux accumulated tons of quirks here.

* * *

### NVIDIA SATA quirks

Historically:

* NCQ bugs,
* DMA weirdness,
* timeout oddities.

If you’re writing your own storage stack:

* keep it simple first,
* avoid SATA advanced features initially.

* * *

### PCI posted writes

NVIDIA chipsets loved aggressive buffering.

When doing MMIO command queues:

* use readbacks as fences,
* don’t assume writes are immediately visible.

* * *

### Documentation quality

Intel chipsets are vastly better documented.

AMD CPU docs: good.  
NVIDIA MCP docs: poor.

Expect reverse engineering and Linux-source archaeology.

# 3. Execute-in-place from FPGA BAR

This is the part where your architecture gets genuinely exotic.

Not impossible.  
But there are several real hazards.

* * *

## First: yes, x86 _can_ execute from PCI MMIO

The CPU does not fundamentally care where instructions come from.

If:

* the BAR is mapped executable,
* paging allows execute,
* the transaction returns bytes,

the core can fetch opcodes there.

Historically:

* option ROMs,
* BIOS shadowing,
* weird embedded systems,
* ROM emulators,  
    all did related things.

So conceptually this is real.

* * *

## The biggest problem: cacheability

This is the central issue.

You do **not** want the region cacheable if:

* ESP32 mutates code asynchronously.

But:

* uncached execution over PCI is _slow_,
* and instruction fetch behaviour gets ugly.

You’re right to think about:

* MTRRs,
* PAT,
* UC/WC/WT semantics.

* * *

## Strong recommendation

Map the BAR as:

```
UC (uncacheable)
```

initially.

Not WC.  
Not WB.

Because otherwise:

* stale I-cache,
* stale data cache,
* speculative fetch,
* reordered visibility,  
    become extremely painful.

* * *

## Instruction prefetch issues

Yes, absolutely real.

The Phenom II frontend:

* fetches ahead,
* predecodes,
* speculates,
* crosses cacheline boundaries.

If the ESP32 mutates code “underneath” execution:

you can absolutely get:

* partially updated instructions,
* stale fetch windows,
* invalid opcode traps,
* speculative execution of garbage.

This is not theoretical.

* * *

## Your architecture therefore needs ownership rules

You need something like:

```
ESP32 writes code
ESP32 sets READY flag
CPU serializes
CPU executes immutable region
CPU signals DONE
ESP32 allowed to modify again
```

Do _not_ allow live mutation of executable bytes.

Treat executable regions as immutable while running.

* * *

## Serialization requirements

Before jumping into freshly written code:

On x86 you want at minimum:

* a full memory fence,
* serialization,
* likely instruction stream flush behaviour.

Typical safe pattern:

```asm
mfence
cpuid
jmp target
```

`CPUID` is serializing.

You may also want:

* self-modifying-code style rules,
* taken branch after write visibility.

* * *

## BAR size / paging

Another issue:

* PCI BAR windows are finite,
* alignment matters,
* chipset decoding granularity matters.

Don’t assume arbitrary huge executable windows.

Legacy PCI systems can be awkward here.

* * *

## DMA vs direct execution

This is the key architectural question:

### Direct execution from BAR

Pros:

* cool,
* exotic,
* true XIP.

Cons:

* slow,
* uncached,
* synchronization hell.

### DMA/copy into RAM then execute

Pros:

* vastly faster,
* cache coherent,
* normal execution semantics.

Cons:

* less philosophically interesting.

For a research/hobby project:  
your approach is valid.

For performance:  
copy-to-RAM wins by miles.

# 4. Realistic PCI bandwidth

Your theoretical number is correct:

Conventional 32-bit 33 MHz PCI:

$$33\times10^6\times4\approx133\times10^6\ \mathrm{bytes/s}$$

~133 MB/s peak bus bandwidth.

But practical sustained throughput is lower.

Realistically expect maybe:

* ~70–110 MB/s sustained reads,
* depending on:
    * wait states,
    * FPGA latency,
    * burst support,
    * chipset behaviour,
    * arbitration,
    * bridge overhead.

For instruction fetch specifically:  
likely much worse than bulk DMA throughput.

Instruction fetches are:

* smaller,
* latency-sensitive,
* less burst-friendly.

So “execute directly from PCI” will feel _dramatically_ slower than RAM.

Potentially by an order of magnitude or more.

# 5. BIOS dump contention diagnosis

Your diagnosis is very plausible.

In fact it’s one of the most common causes of:

* “flashrom sees programmer but no JEDEC ID”.

Unpowered chipsets frequently parasitically clamp SPI lines through:

* ESD diodes,
* input structures,
* partially powered internal domains.

MISO is the usual casualty.

So your reasoning is technically sound.

* * *

## One thing to verify

Make sure:

* your programmer is actually providing VCC to the flash,
* and not brownout-collapsing through the chipset load.

Measure:

* voltage directly at the chip pins during transaction.

A surprisingly common failure mode is:

```
3.3V idle
2.1V during SPI activity
```

because the board is back-powering through protection structures.

* * *

## Other mitigations worth trying

Before desolder:

### Remove ATX battery

Sometimes RTC/standby domains partially bias the chipset.

* * *

### Hold RESET asserted

Can occasionally tristate some chipset IO.

Not guaranteed.

* * *

### Series resistor trick

Sometimes:

* cutting MISO with a temporary resistor network,
* or injecting stronger drive,  
    helps.

But this gets sketchy fast.

* * *

### Power entire board but hold CPU reset

Dangerous territory.

As you suspected:  
once chipset powers,  
its own SPI master may contend.

I would avoid this.

# 6. Lifting only MISO

Yes.  
This is actually a very reasonable intermediate technique.

Often the cleanest compromise.

Advantages:

* preserves physical attachment,
* minimizes pad damage risk,
* isolates the critical contention path.

Usually:

* pin 2 on SOIC-8 SPI flash is DO/MISO.

You:

* lift it,
* wire directly to programmer,
* leave rest attached.

That is a legitimate repair/rework method.

Just be careful:

* Macronix pads lift fairly easily with excess heat.

Use:

* flux,
* low-temp alloy if available,
* magnification.

# 7. Gigabyte DualBIOS behaviour

This is the area where internet folklore gets especially bad.

The important point:

## DualBIOS is _not_ purely hardware.

It is a hybrid:

* bootblock logic,
* BIOS code,
* chipset support,
* board-specific policy.

The exact behaviour varies by generation.

* * *

## What probably happens on your board

Typically:

1. Main BIOS selected at reset.
2. Bootblock executes.
3. Integrity checks occur.
4. If corruption/failure detected:
    * backup BIOS copied into main.

Triggers may include:

* checksum failure,
* failed decompression,
* incomplete POST,
* watchdog-like reboot loops.

Not just “sum != zero”.

* * *

## Important practical reality

Gigabyte boards were infamous for:

* aggressive automatic recovery,
* reflashing main unexpectedly,
* difficult experimentation.

So your concern is justified.

* * *

## Safest workflow

### Best approach:

Physically remove or disable backup chip while experimenting.

Seriously.

Because otherwise:

* the board may “helpfully” overwrite your custom firmware.

Possible approaches:

* remove B_BIOS entirely,
* isolate its CS# line,
* use socket adapters.

* * *

## Also strongly recommended

Use:

* external programmer recovery only.

Do not rely on:

* Q-Flash,
* software flashers,
* recovery logic.

Treat the board as recoverable only via SPI programmer.

# 8. Award checksum semantics

You are correct to distinguish:

* firmware checksum,  
    vs
* hardware validity gating.

The classic:

```
sum(all bytes) == 0 mod 256
```

Award checksum is fundamentally a BIOS-level integrity check.

Not typically a hardware gate enforced before execution.

Meaning:

* CPU still begins executing reset vector,
* bootblock runs,
* BIOS code checks integrity,
* then recovery may trigger.

So:

* a bad checksum may still execute _some_ code first.

This matters for experimentation.
