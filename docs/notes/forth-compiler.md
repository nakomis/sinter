# Forth-to-x86-64 compiler on the ESP32 (SINT-25 design notes)

Design notes for the ESP32-side compiler that turns LLM-generated Forth
into x86-64 machine code for injection into the PCI BAR. Companion to
[[pci-bar-execute.md]] (the execution environment the output runs in).
Nothing here is implemented yet; this is the shape of the thing.

## 1. The one decision that keeps this small

**We control the dialect.** The Forth isn't written by humans with
forty years of ANS Forth habits — it's generated by an LLM from a prompt
*we* write. That means the compiler doesn't need to accept Forth; it
needs to accept *our subset of* Forth, and the prompt can be as
prescriptive as we like about staying inside it.

Consequences:

- **No full ANS Forth.** No `CREATE`/`DOES>`, no wordlists, no
  `EVALUATE`, no interpretation-vs-compilation semantics. If the LLM
  emits a word outside the dialect, that's a *compile error fed back
  into the agentic retry loop* — the same path as a failed validation,
  and exactly what the loop is for.
- **No optimiser.** The Phenom at 3.4 GHz running naive code beats the
  ESP32 spending seconds being clever. Pi digits and Mandelbrots are
  not register-allocation-bound.
- **A weekend-sized compiler, not a year-sized one.** Subroutine
  threading over a fixed primitive set (§2) is a few hundred lines of C.

## 2. Compilation model: subroutine-threaded

Three classic options:

| Model | Output | ESP32-side cost | Why / why not |
|---|---|---|---|
| Token-threaded | bytecode + interpreter | trivial | needs an interpreter *on the Phenom* — now there are two programs to debug |
| Subroutine-threaded | `call prim` per word | small | **chosen** — output is real x86-64, debuggable with a disassembler |
| Native inlining | inlined primitives | large | optimisation we don't need yet; natural upgrade later |

Subroutine-threaded means each Forth word compiles to a `call` to a
primitive, and a colon definition compiles to a sequence of `call`s
ending in `ret`. The injected binary is then: a **primitive library**
(fixed, precompiled blob, identical for every program) followed by the
**compiled program** (a string of `call`s). The ESP32 only ever
generates `call` instructions, literal pushes, and branches — the
hairy x86-64 encoding lives in the precompiled primitives, which are
written once, by hand, and verified with a disassembler.

## 3. Register convention

Keep the Forth VM state in registers the injected code owns outright
(the §3 handshake in [[pci-bar-execute.md]] means the kernel's poll loop
`call`s us and we `ret` — standard SysV callee-saved rules apply):

- `rbp` — data-stack pointer (grows down, in the BAR scratch region)
- `r12` — return-stack pointer (the hardware stack stays the kernel's)
- `rbx` — top-of-stack cached in a register (the classic Forth win)
- `r13` — base address of the BAR scratch/result region

All callee-saved, so the prologue/epilogue saves and restores them and
the kernel never knows. Data stack and return stack live in the BAR
scratch region (`BAR + 0x2000`) — visible to the ESP32 afterwards,
which makes post-mortem debugging of a wrong answer a free SPI read.

## 4. The primitive set

Start indecently small; grow only when a workload demands it:

- **Stack:** `dup drop swap over rot >r r> r@`
- **Arithmetic:** `+ - * / mod negate abs min max 1+ 1-`
- **Logic/compare:** `and or xor invert = <> < > 0= 0<`
- **Memory:** `@ ! c@ c!` (addresses are BAR-relative offsets — the
  injected code never touches arbitrary physical memory)
- **Control:** `if else then begin until while repeat do loop i`
  (compiled to branches by the ESP32, not primitives)
- **Result:** `result!` — store top-of-stack to the result region and
  set the done flag (with the §4 posted-write readback fence from
  [[pci-bar-execute.md]])

Notably absent until proven needed: floating point (Mandelbrot can be
fixed-point first), strings, double-cell arithmetic, `."`-style output
(results come back through the result region, not a terminal).

## 5. What the ESP32 actually emits

1. Copy the precompiled primitive blob to `BAR + 0x1000`.
2. Walk the Forth source token by token:
   - known word → `call <primitive or earlier definition>`
   - number → push literal (`mov`/`push` pair against `rbx`/`rbp`)
   - control word → emit/patch relative branches (one-pass with a
     small fixup stack for forward references)
   - anything else → compile error, returned verbatim to the agentic
     loop as LLM feedback
3. Append the `UD2` guard tail (§2 of [[pci-bar-execute.md]]).
4. Run the status-word handshake (status last).

## 6. Testing without the rig

None of this needs the Phenom, the FPGA, or the PCI bus:

- **Golden tests on the host.** The compiler is plain C — build it for
  the dev machine, compile `: answer 6 7 * result! ;`, and compare the
  emitted bytes against a checked-in golden binary.
- **Execute the output on any x86-64 Linux box** with a 50-line harness
  that `mmap`s an executable buffer, fakes the BAR layout, and calls the
  entry point. The same harness later becomes the validation oracle for
  the agentic loop: ESP32 output and host-Forth output must agree before
  blaming the hardware.
- **Disassemble everything.** `objdump -D -b binary -m i386:x86-64` on
  the emitted blob in every test run; per [[verify-against-silicon.md]],
  the disassembler is a higher authority on what we emitted than our
  own emitter is.

This is the purest software workstream in the project — blocked on
nothing, parallel to all hardware tracks (SINT-93/94/95 and the BIOS
work alike).

## 7. What this file is *not*

A spec. The dialect will bend when the first real LLM transcripts show
what Ollama actually likes to emit; the primitive set will grow when pi
digits demand double-cell maths. Revise freely — but defend §1: every
feature request gets answered with "or we could tighten the prompt".
